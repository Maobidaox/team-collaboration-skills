# 软件开发团队 SOP 工作流

## 概述

以「代码 = SOP(团队)」为理念：将软件开发任务路由到四条标准工作流之一，由四个虚拟角色——产品经理（许清楚）、架构师（高见远）、工程师（寇豆码）、QA 工程师（严过关）——按序协作完成。本 skill 定义路由判定、阶段编排与质量关卡；各角色的详细产出规范在 `references/` 下，进入对应阶段时加载。

## 第一步：工作流路由判定（CRITICAL — 收到请求时首先执行）

| 场景 | 判定条件 | 工作流 |
|------|---------|--------|
| 小型需求 | 单页面应用、小游戏、工具脚本、≤ 10 个源文件 | ⚡ 快速模式 |
| Bug 修复 | 用户报告明确 Bug，非新功能 | 🔧 BugFix 路径 |
| 中大型需求 | 多页面/多模块应用、前后端联动、> 10 个源文件 | 🏗️ 标准 SOP |
| 仅分析 | 仅 PRD / 架构评审 / 市场调研 / 仅测试 | 📋 部分工作流 |

判断原则：

- 单页面 Web 应用、HTML5 小游戏、CLI 工具、简单 CRUD → 快速模式
- 只有涉及复杂多模块交互、微服务、需要架构决策的项目才走标准 SOP
- 宁选快速模式，不选过重流程 — 大多数需求都应走快速模式
- 需求不明确时，先请求澄清再启动工作流
- 多部分请求须逐部分应答或明确标注未解决项

## 第二步：选择执行模式

按当前环境可用的工具选择其一：

### 模式 A：多智能体协作（有 Agent/团队派发能力时优先）

1. 创建团队（命名 `software-<项目简称>`，BugFix 用 `software-bugfix-<问题简称>`），由主理人亲自创建，严禁委派成员创建
2. 按工作流阶段依次派发成员，`name` 与 `subagent_type` 传入角色 ID：`software-product-manager` / `software-architect` / `software-engineer` / `software-qa-engineer`；若所需角色类型不可用，回退模式 B
3. 分派时附带完整需求描述 + 前序阶段的全部产出作为上下文
4. 成员产出回传主理人汇总后再转交下一阶段；禁止成员互相直连通信
5. 禁止主理人代写任何成员的专业产出（PRD/架构设计/代码/测试）

### 模式 B：单智能体分阶段执行（无子代理能力时的等价实现）

1. 按工作流逐阶段推进；进入某角色阶段前，先读取对应 `references/<role>.md` 作为该阶段的行为规范
2. 每个阶段的输出必须符合该角色的产出模板（PRD → 系统设计 + 任务列表 → 代码 → 测试报告）
3. 阶段之间显式执行质量关卡自检，未通过不进入下一阶段

## ⚡ 快速模式（大多数需求的首选）

跳过 PRD 与架构设计：

```
用户需求 → 工程师(一次性实现全部代码) → QA(验证)
```

1. 确认可走快速模式后，将完整需求 + 建议技术栈（默认 Vite + React + MUI + Tailwind CSS）分派给工程师
2. 工程师在一个回合内写完全部文件（遵循 `references/engineer.md` 的 ALL-AT-ONCE 模式）
3. QA 验证通过 → 交付完成

典型场景："帮我开发一个贪吃蛇游戏"、"做一个 Todo 应用"、"写一个 Markdown 编辑器" 均走快速模式；"开发一个电商平台" 走标准 SOP。

## 🔧 BugFix 快捷路径

```
用户 Bug 报告 → 工程师(定位 + 修复) → QA(回归测试)
```

1. 向工程师提供 Bug 描述、重现步骤、期望行为
2. 工程师先读现有代码理解现状，再以最小变更修复（见 `references/engineer.md` 增量开发节）；修源码而非修测试，除非测试明显错误
3. QA 仅运行回归测试确认修复

## 🏗️ 标准 SOP（中大型需求）

```
用户需求 → 产品经理(PRD) → 架构师(系统设计 + 任务分解) → 工程师(代码实现) → QA(测试验证)
```

1. **产品经理**：创建 PRD。默认简单 PRD（产品目标 + 用户故事 + P0/P1/P2 需求池 + UI 草案 + 待确认问题）；仅当用户明确要求详细分析时输出完整 PRD（增加竞品分析 5-7 个 + Mermaid 象限图）。规范见 `references/product-manager.md`
2. **架构师**：基于 PRD 一次性输出系统设计（实现方案 / 文件列表 / 类图 / 时序图 / 待明确事项）+ 任务分解（依赖包列表、有序任务列表、共享知识、依赖图）。规范见 `references/architect.md`
3. **工程师**：按任务列表批量写码，全部完成后执行一次全局一致性审查并输出 IS_PASS: YES/NO；NO 则修复后重审（最多 2 轮）。规范见 `references/engineer.md`
4. **QA**：编写测试用例、运行、做智能路由判定（源码 Bug → 工程师修复 / 测试 Bug → 自行修复 / 全部通过 → 成功报告），最多 2 轮。规范见 `references/qa-engineer.md`

反馈回路：

- QA 发现源码 Bug → 携带失败测试、期望与实际行为、错误信息回派工程师
- 架构师发现 PRD 歧义 → 回派产品经理澄清
- 工程师发现设计问题 → 回派架构师修订

## 📋 部分工作流

并非所有任务都需要完整 SOP，按需裁剪：

- **仅 PRD / 市场调研** → 只执行产品经理阶段（调研模式的报告结构见 `references/product-manager.md`）
- **架构评审** → 只执行架构师阶段
- **代码实现** → 只执行工程师阶段（使用已有设计文档）
- **仅测试** → 只执行 QA 阶段

## 质量关卡（铁律汇总）

| 关卡 | 规则 |
|------|------|
| 任务分解 | 任务数 ≤ 5；首个任务必须是项目基础设施（配置 + 入口 + 依赖声明合为一个任务）；禁止一文件一任务；禁止把配置文件分散到多个任务 |
| 代码完整性 | 禁止 pass / TODO / 占位符；实现设计文档定义的全部类与函数；严格遵守类图与接口签名 |
| 一致性审查 | 全部文件写完后做一次全局跨文件审查（导入一致性 / 接口契约 / 数据流 / 无重复实现），输出 IS_PASS: YES/NO，最多 2 轮 |
| 测试轮次 | QA 最多 2 轮；第 2 轮仍失败则立即退出，在报告中标注 Known Issues，不再继续调试 |
| 测试路由 | 断言符合设计但实现错误 → 回派工程师；断言本身错误 → QA 自修；全部通过 → 成功报告 |
| 信息流转 | 多智能体模式下所有跨成员信息经主理人中转；所有输出语言与用户需求一致 |
| 效率优先 | 在保证质量的前提下减少不必要的轮次与冗余步骤 |

## 增量开发支持

在已有项目上提出变更需求时：

1. **产品经理**：基于旧 PRD + 新需求生成增量 PRD（仅描述变更部分）
2. **架构师**：基于旧设计 + 增量 PRD 生成增量设计 + 增量任务列表
3. **工程师**：先读现有代码，最小变更原则修改（不整体重写文件），明确记录改动点与理由
4. **QA**：运行全量回归测试 + 新功能测试

## 交付规范

工作流完成后向用户汇报：

- **TL;DR**：一句话说明交付了什么
- **交付概览**：交付状态、测试通过率、已知问题数
- **文件清单**：所有创建/修改的文件路径
- **下一步建议**：3-5 条（启动命令、部署建议等）

仅当用户明确要求生成报告文件时，才落盘到 `deliverables/<项目简称>-delivery-<YYYY-MM-DD>.md`；默认不自动生成。
