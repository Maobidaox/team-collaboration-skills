# 实时能力与生产加固（Phase 4 + 上线前）

## 一、实时方案选型：三选一，别默认上 WebSocket

| 方案 | 方向 | 适用 | 代价 |
|------|------|------|------|
| **轮询** | 客户端主动拉 | 更新频率低（>10s）、可容忍延迟 | 无效请求多，间隔难调 |
| **SSE** | 服务端单向推 | 通知、进度、日志流、行情推送（**不需要客户端反向发**） | 单向；走 HTTP，穿透性好 |
| **WebSocket** | 双向 | 聊天、协同编辑、多人游戏、需要客户端高频反向发 | 连接管理复杂，需自己做心跳与重连 |

**决策顺序**：能轮询就轮询 → 需要服务端推且单向就用 SSE（实现成本远低于 WS）→ 只有真正需要双向低延迟才用 WebSocket。

### 轮询

间隔用**指数退避 + 抖动**：无变化时逐步拉长（1s → 2s → 4s → 上限 30s），有变化立即回落。页面不可见时（`visibilitychange`）暂停。

### SSE（常被低估）

```ts
// 服务端：注意三个关键点
res.writeHead(200, {
  'Content-Type': 'text/event-stream',
  'Cache-Control': 'no-cache, no-transform',  // ★ 关掉缓冲，否则代理会攒着不发
  'Connection': 'keep-alive',
  'X-Accel-Buffering': 'no',                  // ★ Nginx 下必须，否则被缓冲
});
const keepAlive = setInterval(() => res.write(': ping\n\n'), 15_000); // 心跳防空闲断连
req.on('close', () => { clearInterval(keepAlive); unsubscribe(); });  // ★ 必须清理
```

客户端用 `EventSource`（自带断线重连，浏览器原生支持）。注意：`EventSource` 不能自定义请求头 → 需要鉴权时改用 Cookie 或换 fetch 流式读取。

### WebSocket

必须自建三件事，缺一件线上必然出问题：

1. **心跳** —— 服务端定时 ping，客户端超时未收到则判定断线
2. **断线重连** —— 指数退避（1s/2s/4s…上限 30s）+ 随机抖动（防雪崩重连）
3. **重连后补偿** —— 断线期间的消息会丢，重连后按 `lastEventId` 或时间戳拉取增量，不要假装没断过

```
连接状态机：connecting → open → (心跳正常) → closed/unstable → 退避重连 → open → 增量同步
```

**常见坑**：只在前端写重连、服务端不清理断开的订阅 → 连接泄漏，内存与消息数持续上涨。服务端必须在 `close` 事件里 unsubscribe + 清定时器。

## 二、长任务与后台任务

- 请求处理器**只做投递**（写入队列表 / 发消息），立即返回 `202 Accepted` + 任务 ID
- 任务**幂等**：同一任务 ID 重复执行结果一致（用唯一键或状态机保护）
- 失败重试：有限次数 + 指数退避；超过上限进**死信队列**，可人工干预重放
- 任务进度写库或通过 SSE 推给前端，不要靠「前端一直转圈等着」

## 三、上线前加固清单

| 类别 | 项 | 验证方式 |
|------|---|---------|
| 配置 | 全部来自环境变量，启动校验通过 | 删变量 → 快速失败 |
| 密钥 | 无硬编码，`.env` 在 `.gitignore`，仓库无真实密钥 | `git log -p` 扫一遍 + grep |
| 错误 | 客户端看不到堆栈与内部细节 | 制造异常 → 检查响应体 |
| 日志 | JSON 结构化 + requestId + 敏感字段脱敏 | 触发一次登录，检查日志无密码 |
| 数据库 | 迁移可回滚，连接池有上限 | 执行 down 再 up |
| 认证 | 默认全鉴权 + 白名单放行 | 未带令牌访问受保护路由 → 401 |
| CORS | 显式来源，生产无 `*` | 从非白名单来源发请求 → 被拒 |
| 安全头 | HSTS / CSP / X-Content-Type-Options | `curl -I` 检查响应头 |
| 限流 | 登录、短信、写接口有频控 | 连续请求 → 429 |
| 健康检查 | `/health` 不查依赖、`/ready` 查依赖 | 分别 curl |
| 优雅停机 | SIGTERM 后停止接新请求、在途请求完成 | `kill -TERM` 观察日志 |
| 传输 | 强制 HTTPS，HTTP 重定向 | `curl -I http://` → 301/308 |
| 备份 | 数据库定时备份 + 已验证可恢复 | 做一次恢复演练（没演练过的备份不算备份） |

## 四、回滚预案（上线前必须写下来）

发布前先回答三个问题，答案写进发布记录：

1. **触发条件** —— 什么指标算失败（错误率 >1%、P95 延迟翻倍、关键接口 5xx）？
2. **回滚动作** —— 切上一版镜像/代码？数据库向下兼容，还是需要先回滚迁移？
3. **回滚时限** —— 从发现到完成需要几分钟？谁有权执行？

**数据库迁移原则**：先扩展（加字段/新表，新旧代码都能跑）→ 再切代码 → 确认稳定后收缩（删旧字段）。**上线与删字段不要在同一次发布里做**，否则无法回滚。

## 五、容量与性能的常识阈值

- 接口 P95 延迟：列表类 <300ms，详情类 <100ms，写操作 <500ms
- 数据库单表行数超千万、或单表超 50GB → 该考虑分区/归档，而不是继续加索引
- 连接池 `max` ≈ 数据库可用连接数 / 实例数，留 20% 余量给运维与迁移
- 一个请求内的数据库往返超过 5 次 → 先查是不是 N+1 或缺批量接口
