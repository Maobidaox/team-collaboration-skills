# 架构与实现检查点

## 从业务不变量开始

在选框架模式前，写清：

- 哪些状态转换合法，谁有权触发。
- 哪些写入必须原子完成。
- 重复、乱序、延迟、部分失败时应发生什么。
- 哪个系统是事实来源，读写一致性要求是什么。
- 哪些外部契约必须保持兼容。

## API

- 明确请求/响应 schema、必填项、范围、默认值、错误码和授权。
- 更新操作区分 PUT/PATCH 语义；分页必须有稳定排序。
- 创建或支付类操作需要幂等键、重复请求语义和保留周期。
- 兼容演进优先新增可选字段；删除/重命名需迁移期与消费者确认。
- 不把内部异常、表结构、堆栈或敏感标识直接暴露给调用方。

## 分层与依赖

- 依赖方向应让业务规则能独立测试；框架类型不要无必要渗入领域核心。
- Controller/Listener 负责协议适配、鉴权上下文和输入边界；不承载复杂业务编排。
- Repository 表达持久化需求，不让调用方依赖查询实现细节。
- 只有出现明确替换点、独立演进边界或测试收益时才新增抽象。

## 事务与一致性

- 标记事务入口、数据库写入、外部副作用和提交时点。
- 事务内发布消息可使用 outbox/事务事件等保证；不要宣称普通数据库事务能回滚外部 HTTP 调用。
- 分布式流程优先设计幂等、补偿和状态机，再考虑锁或全局事务。
- 明确传播行为与异常回滚规则；检查 Spring 代理自调用导致注解失效的问题。
- 长事务会占用连接、扩大锁范围；外部慢调用通常应移出事务或设定严格边界。

## 数据库

- 约束是数据不变量的最后防线：唯一性、非空、外键或等价校验应与业务规则一致。
- 索引顺序由实际谓词、排序和选择性决定；用执行计划验证。
- 分页避免不稳定排序和深 offset 问题；大数据导出采用流式/分批且设置资源上限。
- 迁移遵循扩展—切换—收缩：先增加兼容结构，双写/回填/切读，最后删除旧结构。
- ORM 审查 N+1、抓取范围、批量写、级联、脏检查、锁模式和分页联表行为。

## 缓存

- 记录缓存目的、键组成、TTL、最大规模、序列化版本和失效触发器。
- 处理击穿、穿透、雪崩、热点键与缓存污染。
- 缓存失败时明确降级路径；不要让缓存成为唯一数据来源，除非系统设计明确如此。
- 更新顺序与一致性窗口必须符合业务容忍度。

## 消息与异步

- 声明交付语义、分区/顺序、去重键、重试次数、退避、死信与人工重放流程。
- 消费者在崩溃重启和重复投递下仍应满足业务不变量。
- 事件 schema 版本化；生产者与消费者独立升级时保持兼容。
- 线程池和队列必须有界；拒绝时是阻塞、降级、失败还是持久化，需显式决定。

## 配置与可观测性

- 配置项使用类型、范围和启动时校验；秘密只引用环境或密钥管理系统。
- 日志包含可关联的请求/业务标识，但过滤令牌、密码、个人数据和大对象。
- 关键路径至少能观察成功率、错误分类、延迟、吞吐和饱和度。
- 告警面向用户影响或资源耗尽，不为每个单次可恢复异常制造告警。

## 实施前的最小风险表

| 风险 | 触发条件 | 影响 | 防护/验证 |
|---|---|---|---|
| 重复提交 | 客户端重试或消息重复 | 重复写/扣减 | 幂等键、唯一约束、回归测试 |
| 部分失败 | 数据库成功、外部调用失败 | 状态不一致 | 状态机/outbox/补偿测试 |
| 兼容破坏 | 新旧版本并存 | 请求或消息解析失败 | 扩展式 schema、契约测试 |
| 资源耗尽 | 无界输入/队列/查询 | 延迟飙升或 OOM | 上限、分页、背压、压测 |
