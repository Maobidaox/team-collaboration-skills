# 框架选型与项目结构（Phase 1）

## 决策树

```
内容是否需要服务端动态渲染 / SEO 强依赖？
├─ 否，纯静态内容为主（博客、文档、落地页、作品集）
│   └─ 选 Astro（默认零 JS，按需岛屿 hydration）或纯 HTML + CSS
├─ 是，且需要复杂交互 / 数据获取 / 路由 / 服务端渲染
│   ├─ 需要 SSR / ISR / API 路由 / 完整全栈能力 → Next.js 或 Remix
│   └─ 只需单页应用壳，后端已有独立服务 → Vite + React / Vue（SPA）
└─ 内容驱动 + 少量交互 + 团队偏 Vue 生态 → Vue / Nuxt 或 Astro + Vue 岛屿
```

选型要素：内容更新频率、SEO 权重、交互复杂度、团队熟悉度、部署平台约束（如纯静态托管不支持 SSR）。选型结论要写清理由与备选方案，让用户有能力否决。

## 主流方案对比

| 方案 | 渲染 | 交互成本 | SEO | 部署 | 适用 |
|------|------|---------|-----|------|------|
| 纯 HTML/CSS | 静态 | 手写 JS | 好 | 任意静态托管 | 单页、落地页、极简需求 |
| Astro | 静态 + 岛屿 | 低 | 好 | 静态托管 / 适配器 | 内容站、博客、文档、营销站 |
| Next.js | SSG / SSR / ISR | 中 | 好 | Vercel 或 Node 运行时 | 应用级、需要 API 路由与 SSR |
| Remix | SSR 优先 | 中 | 好 | Node 运行时 | 表单密集、渐进增强应用 |
| Vite + React/Vue | CSR (SPA) | 低 | 需额外处理 | 任意静态托管 | 后台系统、重交互轻 SEO |

## 目录结构约定

以 Next.js App Router 为例（其他框架按同类约定调整）：

```
app/                  # 路由与页面（layout / page / loading / error）
  layout.tsx          # 根布局：html/body、全局样式、元数据
  page.tsx            # 首页
components/           # 可复用组件（按功能域分子目录）
lib/ 或 utils/        # 纯函数、数据访问、API 客户端
public/               # 静态资源（会被原样拷贝到根路径）
styles/               # 全局样式与 design token
```

约定：组件与样式同域放置；数据获取集中在 `lib/`；跨页面的共享状态用明确的状态管理方案，不滥用全局 store。

## 数据流与依赖

- **数据获取**：明确发生在哪一层（服务端组件 / 路由 loader / 客户端 effect），避免同一数据在两端重复获取
- **状态管理**：本地状态优先（`useState` / `ref`），跨组件才提升到 Context 或 store；服务端数据优先用数据请求库（React Query / SWR）而非手写 effect
- **关键依赖**：只引入必需依赖，标注版本范围；构建体积敏感的依赖（图标库、日期库、动画库）按需引入

## 交付说明要点

给出方案时一并提供：目录结构、关键依赖及用途、数据流图（请求从哪来、数据到哪去）、以及分期实施步骤。
